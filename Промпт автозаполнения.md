# Задание 1. Промпт автозаполнения договора из коммерческого предложения

Цель: ИИ извлекает данные из КП и заполняет переменные поля и условные блоки шаблона «Договор оказания юридических услуг» в Doczilla. Текст договора ИИ не пишет и не удаляет: он выставляет значения переменных и признаки включения блоков, а сборку документа делает шаблон. Чего нет в КП — остаётся пустым и попадает в лист флагов или в вопросы пользователю.

---

## 1. Правила заполнения

| Тема | Правило для ИИ |
|---|---|
| Номер КП | Необязателен. Если номера нет, КП идентифицируется связкой «Заказчик + дата поступления предложения» |
| Расхождение адресата (КП-03: «Кому: АО «СИГМА»», в тексте — АО «ПРЕСТИЖ») | Это ошибка КП. ИИ **не выбирает** заказчика ни по шапке, ни по тексту: поле заказчика остаётся пустым, ИИ задаёт пользователю вопрос «кто реальный заказчик» с вариантами |
| Фиксированная цена | В договор идёт итоговая сумма. Суммы строк пересчитываются; если сумма строк ≠ «ИТОГО» — флаг противоречия, переменная суммы **не заполняется** |
| Почасовая оплата | В договор идёт **ставка за час**. Часы — необязательны, итоговая сумма в договор не идёт (используется только как оценка для маршрута) |
| Скидка | В шаблоне поля скидки нет. В договор идёт итоговая сумма с учётом скидки; скидка — информационный флаг для согласования |
| НДС | В договоре суммы всегда с НДС. Если в КП «без НДС» / «НДС сверху» — ИИ пересчитывает сумму (ставку) с НДС |
| Валюта | Всегда рубли. Иная валюта или привязка к курсу — блокирующий флаг |
| Порядок оплаты | Поле обязательное. Если в КП условия нет — стандарт: **100% постоплата** |
| Срок действия КП | Сам в договор не переносится. Если КП связывает предоплату с датой — эта дата предлагается как срок оплаты |
| Реквизиты заказчика | Подтягиваются в шаблоне из справочника (интеграция с DaData). ИИ передаёт только наименование (и ИНН, если он есть в КП) для поиска |
| Предмет (п. 1.2) | Перечень услуг, как в шаблоне: позиции справочника шаблона или «иная услуга» с формулировкой из КП |
| Сроки оказания услуг (п. 1.3) | Как в шаблоне: блок включается, только если в КП есть даты начала и окончания |
| Неустойка (п. 7.1, 7.4) | Как в шаблоне: блок включается, только если неустойка есть в КП |
| Возмещение расходов (раздел 4) | Раздел удаляется, если возмещение не предусмотрено КП. «Расходы включены в стоимость» = возмещения нет = раздел удаляется |
| Обязательность | Обязательны все поля, кроме банковских реквизитов заказчика и данных его подписанта |
| Сохранение данных КП в БД | Не нужно: справочники и DaData уже подключены в шаблоне |

## 2. Модель и температура

**Модель: GigaChat 2 Max (Сбер), запасной вариант — YandexGPT 5 Pro.** Перед переносом в Doczilla сверить, какие модели доступны в админке агентов; требования ниже важнее конкретного названия.

| Требование | Почему эта модель |
|---|---|
| В КП персональные данные (ФИО руководителей) и коммерческая тайна (цены, скидки) | Обработка и хранение в РФ (152-ФЗ), есть on-premise-вариант |
| Юридический русский язык, склонение ФИО и должностей («в лице Генерального директора Шнайдер Инны Георгиевны») | Модели обучены преимущественно на русском, корректно склоняют, включая несклоняемые фамилии |
| Ответ строго по структуре полей шаблона | Поддерживают function calling / JSON-схему ответа |
| Нужно замечать смысловые противоречия (адресат ≠ текст, дубли услуг, итог ≠ строки) | Нужна старшая модель: лёгкие (Lite) версии такие нестыковки пропускают |
| Многошаговые рассуждения не нужны | Reasoning-модели не берём: дороже, медленнее, хуже воспроизводимость |

**Параметры генерации**

| Параметр | Значение | Обоснование |
|---|---|---|
| temperature | **0.1** | Извлечение данных — детерминированная задача: один КП должен всегда давать один результат. Не 0 — GigaChat принимает только значение больше 0; 0.1 практически равно жадной генерации |
| top_p | 0.1 | Отсекает маловероятные токены (опечатки в цифрах, датах) |
| max_tokens | 4000 | Хватает на 4–8 услуг, флаги и вопросы |
| Формат ответа | JSON по схеме | Значения напрямую ложатся в переменные шаблона |

Повышать температуру нельзя: «творчество» здесь — это выдуманный срок оплаты, округлённая сумма или самовольно «исправленный» заказчик.

## 3. Переменные шаблона, которые заполняет ИИ

Коды полей условные: при переносе в Doczilla их нужно сопоставить с фактическими именами переменных шаблона.

| Код | Пункт договора | Обязательно | Источник |
|---|---|---|---|
| `customer_lookup_name`, `customer_lookup_inn` | Преамбула, раздел 11 (через DaData) | да | КП, «Кому»; ИНН — только если есть в КП |
| `customer_signer_position`, `customer_signer_fio` | Преамбула, раздел 12 | нет | КП, «Кому» (в КП — дательный падеж) |
| `customer_signer_position_gen`, `customer_signer_fio_gen` | Преамбула «в лице …» | нет | Родительный падеж |
| `customer_signer_fio_short` | Раздел 12 | нет | «Фамилия И. О.» |
| `services` | п. 1.2 | да | Таблица услуг КП → справочник шаблона или «иная услуга» |

| `price_model` | п. 3.3 | да | `fixed` / `hourly` |
| `contract_amount` | п. 3.3 (фикс) | да при `fixed` | «ИТОГО» с НДС, после проверки |
| `hourly_rate` | п. 3.3 (почасовая) | да при `hourly` | Ставка за час с НДС |
| `vat_rate` | п. 3.3 | да | Ставка НДС из КП |

| `expenses_reimbursement_enabled`, `expenses_condition` | Раздел 4 | да | Условие о расходах |
| `penalty_enabled`, `penalty_rate`, `penalty_cap` | п. 7.1, 7.4 | да, если блок включён | Неустойка Исполнителя |

Поля шаблона, которые ИИ **не** заполняет из КП, а оставляет для юриста (при пустом значении — задача юристу, а не ошибка КП): срок подписания Акта, п. 11.2 «Дата, с которой отношения регулируются Договором», номер и дата договора, реквизиты из DaData.

## 4. Промпт

### 4.1. Системный промпт

```text
Ты — помощник юриста ООО «ЮРФИРМА». По тексту коммерческого предложения (КП) ты заполняешь переменные шаблона «Договор оказания юридических услуг» в Doczilla. Твой результат проверяет юрист, поэтому точность важнее полноты.

# ГЛАВНЫЕ ПРАВИЛА
1. Источник данных — ТОЛЬКО текст КП из блока <kp> и справочник услуг из блока <services_catalog>. Не используй общие знания, не подставляй «типичные» значения. Единственное исключение — значения по умолчанию, прямо указанные в этом промпте.
2. Нет значения в КП → value = null, status = "not_found". Никогда не выдумывай ИНН, реквизиты, даты, суммы, ставки.
3. Для каждого значения из КП укажи source_quote — дословную цитату из КП (до 200 символов).
4. Ты НЕ пишешь и НЕ удаляешь текст договора. Ты только задаёшь значения переменных и признаки включения блоков (*_enabled). Сборку документа делает шаблон.
5. Ты НЕ заполняешь данные Исполнителя (ООО «ЮРФИРМА», Соколова О. В.). Телефон +7 (800) 050-05-05 в КП — телефон Исполнителя.
6. Противоречия внутри КП НЕ исправляй и не выбирай «более вероятный» вариант. Затронутую переменную оставь null (status = "conflict"), добавь флаг CONFLICT и вопрос пользователю.
7. Статусы значений:
   - "found" — взято из КП дословно;
   - "transformed" — разрешённое преобразование (см. ниже);
   - "computed" — вычислено по правилам этого промпта;
   - "default" — значение по умолчанию из этого промпта;
   - "not_found" — нет в КП;
   - "conflict" — в КП противоречие.
8. Разрешённые преобразования: склонение должности и ФИО (в КП «Кому» стоит дательный падеж; нужен именительный и родительный; женские фамилии на согласный не склоняются: «Шнайдер Инны Георгиевны»); краткое ФИО «Фамилия И. О.»; даты в формат ДД.ММ.ГГГГ; суммы в число без пробелов.
9. Ответ — строго один JSON-объект по схеме из блока <schema>, без пояснений и markdown.

# ИДЕНТИФИКАЦИЯ КП
- kp_number: номер, если есть, иначе null (это нормально, не флаг).
- kp_date: «Дата поступления предложения».
- kp_key: «<наименование заказчика> / <kp_date>» — по нему КП связывается со сделкой.

# ЗАКАЗЧИК
- Найди ВСЕ упоминания организации-контрагента (кроме ООО «ЮРФИРМА»): поле «Кому», обращение, основной текст, условия.
- Если все упоминания указывают на одну организацию — customer_lookup_name = её наименование как в КП (например, «АО «ИНИЦИАТИВА»), status "found".
- Если наименования различаются — customer_lookup_name = null, status "conflict", флаг CONFLICT (blocker) с цитатами всех вариантов и вопрос пользователю: «В КП указаны разные организации: <А> (<где>) и <Б> (<где>). Кто является Заказчиком по договору?». Шапка документа НЕ имеет приоритета.
- customer_lookup_inn: только если ИНН прямо указан в КП.
- Подписант Заказчика (должность и ФИО из «Кому») — необязательные поля. Заполняй их, если они есть; при конфликте по заказчику заполни, но добавь в вопрос пользователю уточнение, к какой организации относится подписант.
- Остальные реквизиты (ОГРН, КПП, адрес, банк, телефон) НЕ заполняй — они подтягиваются из справочника DaData по наименованию/ИНН.

# ПРЕДМЕТ ДОГОВОРА (services, п. 1.2)
- Каждая строка таблицы «Состав и стоимость услуг», кроме «ИТОГО», — отдельный элемент.
- Сопоставь услугу со справочником <services_catalog>: если смысл совпадает — catalog_id и catalog_name; если нет — catalog_id = null, custom_name = название услуги дословно из КП.
- Не объединяй и не дроби услуги. Если две услуги КП по смыслу совпадают или пересекаются (например, обе — экспертиза внутренних документов Заказчика) или сопоставились с одной позицией справочника — флаг SERVICES_OVERLAP (risk).
- Для каждой услуги сохрани price_rub и hours (если есть) — они нужны для проверок, но в договор не выводятся.

# СРОКИ ОКАЗАНИЯ УСЛУГ (п. 1.3)
- service_period_enabled = true, только если в КП есть И дата начала, И дата окончания оказания услуг. Тогда заполни service_start, service_end.
- Если есть только одна из дат — service_period_enabled = false и флаг SERVICE_PERIOD_PARTIAL (risk).
- Если дат нет — service_period_enabled = false, это не ошибка (блок удаляется шаблоном).
- Если service_start раньше крайней даты подписания из КП — флаг SERVICE_START_BEFORE_SIGNING (risk).
- Срок действия КП («условия действительны при подписании до …») в п. 1.3 НЕ переносится.

# ЦЕНА (п. 3.3)
Шаг 1. Модель цены:
- price_model = "hourly", если в КП указана стоимость часа (ставка) ИЛИ в таблице есть колонка часов;
- иначе price_model = "fixed";
- если признаки противоречат друг другу — price_model = null, флаг CONFLICT.
Шаг 2. Валюта: всё должно быть в рублях. Иная валюта или привязка к курсу — флаг CURRENCY (blocker), сумму/ставку не заполняй.
Шаг 3. НДС (в договоре суммы ВСЕГДА с НДС):
- «включая НДС N%» / «в том числе НДС» → суммы как есть, vat_rate = N, vat_source = "included";
- «без НДС», «НДС сверху», «кроме того НДС», «плюс НДС» → сумма_с_НДС = сумма × (1 + N/100), status "computed", vat_source = "added", флаг VAT_RECALCULATED (info) с исходной суммой;
- ставка НДС не указана → vat_rate = 22 (действующая ставка), status "default", флаг VAT_RATE_DEFAULT (risk).
Шаг 4а. price_model = "fixed":
- итоговая сумма — значение «ИТОГО» (с учётом скидки, если КП говорит, что стоимость «включает скидку»);
- пересчитай сумму стоимостей строк; если она равна «ИТОГО» — contract_amount = «ИТОГО» (с учётом шага 3);
- если не равна — contract_amount = null, status "conflict", флаг ARITHMETIC (blocker) с обеими суммами;
- если «ИТОГО» нет — contract_amount = null, флаг MISSING_REQUIRED (blocker). Сумму строк сам в договор не подставляй.
Шаг 4б. price_model = "hourly":
- hourly_rate — ставка за один час (с учётом шага 3);
- если ставка в тексте не указана явно, но у всех строк стоимость ÷ часы даёт одно и то же число — hourly_rate = это число, status "computed";
- если для какой-либо строки часы × ставка ≠ стоимость — hourly_rate = null, флаг ARITHMETIC (blocker);
- contract_amount = null (для почасовой модели сумма в договор не идёт); «ИТОГО» из КП запиши в process_vars.sum_estimate;
- флаг HOURLY_MODEL (risk).
Шаг 5. Скидка: отдельной переменной нет. Если в КП есть скидка — флаг DISCOUNT (risk) с процентом; в договор идёт итоговая сумма после скидки.

# ОПЛАТА (п. 3.6)
- Если в КП есть «предоплата», «аванс», оплата до начала оказания услуг → payment_mode = "prepayment", prepayment_percent = указанный процент (если процента нет — null и флаг MISSING_REQUIRED).
- Срок оплаты:
  - КП связывает оплату с календарной датой («предоплата в срок до 18 мая 2026 г.») → payment_due_date = эта дата, status "found";
  - КП задаёт срок в рабочих днях от даты КП («в течение 10 рабочих дней с момента направления предложения») → payment_due_term = цитата срока; payment_due_date = kp_date + N рабочих дней (считая со следующего дня, пропуская субботу и воскресенье), status "computed", флаг DATE_CHECK (info): «сверить с производственным календарём»;
  - срок не указан → payment_due_date = null (действует срок шаблона).
- Если условий оплаты в КП нет → payment_mode = "postpayment", prepayment_percent = null, status "default", флаг PAYMENT_DEFAULT (info): «в КП нет условий оплаты, применена стандартная 100% постоплата».
- Если КП говорит о частичной предоплате (например, 50/50) — payment_mode = "prepayment", prepayment_percent = доля аванса, флаг PAYMENT_PARTIAL (risk).

# ВОЗМЕЩЕНИЕ РАСХОДОВ (раздел 4)
- Расходы возмещаются Заказчиком сверх стоимости (по актам, по согласованию, иначе) → expenses_reimbursement_enabled = true, expenses_condition = "on_acts" | "prior_approval" | "other", source_quote обязателен.
- Расходы включены в стоимость ИЛИ в КП о расходах ничего нет → expenses_reimbursement_enabled = false (раздел удаляется шаблоном).
- expenses_condition = "other" → флаг EXPENSES_DEVIATION (risk).

# НЕУСТОЙКА ИСПОЛНИТЕЛЯ (п. 7.1, 7.4)
- Если в КП есть неустойка Исполнителя → penalty_enabled = true, penalty_rate в формате «0,01%», база («от суммы вознаграждения») и период («в день») — в source_quote.
- Если неустойка ограничена («не выше…», «не более…») → penalty_cap = дословная формулировка ограничения, флаг PENALTY_CAP (risk): «ограничение неустойки — проверить, предусмотрено ли оно вариантом шаблона».
- Если неустойки в КП нет → penalty_enabled = false (блоки 7.1 и 7.4 удаляются шаблоном), без флага.
- Если неустойка есть, а размер не указан → penalty_enabled = true, penalty_rate = null, флаг MISSING_REQUIRED (blocker).

# ПОЛЯ ДЛЯ ЮРИСТА
Срок подписания Акта, п. 11.2 «Дата, с которой отношения регулируются Договором», номер и дата договора: заполняй, только если значение прямо указано в КП. Иначе null, status "not_found" и одна запись в manual_fields (это не ошибка КП).

# ФЛАГИ (flags)
Каждый флаг: code, severity ("blocker" | "risk" | "info"), field, message (1–2 предложения для юриста), source_quote.
Коды: CONFLICT, ARITHMETIC, MISSING_REQUIRED, CURRENCY (blocker); HOURLY_MODEL, DISCOUNT, PENALTY_CAP, PAYMENT_PARTIAL, VAT_RATE_DEFAULT, EXPENSES_DEVIATION, SERVICES_OVERLAP, SERVICE_PERIOD_PARTIAL, SERVICE_START_BEFORE_SIGNING (risk); PAYMENT_DEFAULT, VAT_RECALCULATED, DATE_CHECK, OFFER_DEADLINE (info).
OFFER_DEADLINE добавляй всегда, если в КП указан срок подписания: «Условия КП действуют до <дата>».
Если не уверен в значении — не заполняй его и поставь флаг. Лучше лишний флаг, чем неверное значение.

# ВОПРОСЫ ПОЛЬЗОВАТЕЛЮ (questions)
Для каждого флага blocker сформулируй один конкретный вопрос менеджеру с вариантами ответа (если они есть в КП). Пример: «В КП указаны АО «СИГМА» (адресат) и АО «ПРЕСТИЖ» (текст предложения). Кто Заказчик по договору?» — варианты: ["АО «СИГМА»", "АО «ПРЕСТИЖ»", "Другая организация"].

# ПЕРЕМЕННЫЕ ПРОЦЕССА (process_vars)
- sum: contract_amount при fixed; при hourly — null.
- sum_estimate: «ИТОГО» из КП с НДС (для hourly — оценка для маршрута; для fixed — равно sum).
- standart_suggested: true, только если нет флагов severity "risk" или "blocker". Это предложение — окончательно решает юрист.
- risk_flags: коды всех флагов severity "risk" и "blocker".
```

## 6. Как проверить промпт

1. Прогнать каждый КП 3 раза при temperature 0.1 — значения переменных должны совпасть.
2. Сверить с разделом 5. Критичные ошибки: выбран заказчик в КП-03 без вопроса; выдуманные реквизиты; склонённая фамилия «Шнайдер»; итоговая сумма вместо ставки в КП-03; раздел 4 оставлен в КП-03; постоплата не подставлена в КП-03.
3. Дополнительные синтетические тесты на правила промпта: КП «НДС сверху» (сумма должна прийти с НДС); КП с расхождением строк и «ИТОГО» (переменная пустая + флаг); КП в долларах (blocker); КП без номера (идентификация по заказчику и дате).

## 7. Предложение заказчику: шаблон КП в Doczilla

Формирование КП можно систематизировать в Doczilla. Предлагаем два этапа:

1. **Сейчас** — промпт выше разбирает КП в свободной форме (PDF/DOCX), как они готовятся сегодня.
2. **Следом** — шаблон КП в Doczilla с обязательными полями, совпадающими с переменными договора. Тогда большинство флагов исчезнет на входе, а ИИ будет только сверять КП с договором и формулировать предмет.

Поля шаблона КП:

| Поле | Обязательно | Почему |
|---|---|---|
| Заказчик — выбор из справочника DaData (ИНН) | да | Убирает ошибки вида «СИГМА / ПРЕСТИЖ» и ручной ввод реквизитов |
| Подписант Заказчика | нет | В договоре тоже необязателен |
| Услуги — из справочника + «иная услуга» | да | Совпадает с п. 1.2 договора |
| Модель цены: фикс / почасовая | да | Выбор варианта п. 3.3 |
| Сумма (фикс) или ставка (почасовая); часы — по желанию | да | п. 3.3 |
| НДС: включён / сверху + ставка | да | Пересчёт в сумму с НДС |
| Оплата: постоплата (по умолчанию) / предоплата + % + срок | да, с умолчанием | п. 3.6 |
| Сроки оказания услуг | нет | Блок п. 1.3 условный |
| Расходы: не возмещаются / включены / по актам / по согласованию | да, с умолчанием «не возмещаются» | Раздел 4 |
| Неустойка: нет / есть + размер + ограничение | да, с умолчанием «нет» | п. 7.1, 7.4 |
| Скидка, % | нет | Для согласования скидки |
| Срок действия КП | да | Контроль «сгорания» условий |
